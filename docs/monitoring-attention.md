# User Monitoring attention indicators

The web Monitoring detail page reuses its existing assessment (the same engine
and server-summary model as Dashboard). No thresholds, rules, classifications,
database writes or subscriptions are added.

- A warning/critical notice above the readings includes **Check Recommendations**.
  Existing aquarium-focus navigation preserves the selected aquarium.
- Affected valid reading/output cards use matching borders and text/icon badges.
- **Readings needing attention** is directly below the grid, before the profile.
  Critical findings come first. Each entry shows the assessed value, configured
  limits when available, and the existing assessment explanation.
- Limits come from the existing `getEffectiveThresholds` helper and loaded
  configuration; missing limits are explicitly unavailable, not guessed.
- Invalid sensor samples are excluded from water-condition findings. A separate
  **Sensor checks needed** section lists diagnostic issues. Fault-only notices
  link to Assessment, rather than promising a water-condition solution.
- Stale/offline data removes current findings/highlights and shows a connection
  notice. Fresh normal recovery removes the warning/critical summary.
- Wording invites review of available approved recommendations. It does not
  guarantee a solution, invent guidance or bypass rule approval.

Authentication, aquarium isolation, manual actions, firmware, Firebase rules,
and backend behavior are unchanged. The volume/loss UI remains hidden. This
changes web user Monitoring, not admin inventory or shared/mobile rule logic.

Isolated UI tests cover banners, ordering, configured/missing limits, highlight
badges, mixed sensor faults, recovery, stale data, and selected-aquarium links.
Existing hidden-volume and manual-control regression tests remain in place.
No production data or equipment commands are generated by the tests. Signed-in
browser review and physical sensor behavior require separate verification.
